## Cover note (draft)

Submitted for the public record by a practitioner who builds
and operates agentic systems: a local-model agent runtime
with deterministic, operator-approved action gating; a
brokered tool-mediation layer for a commercial game engine's
MCP surface; and a fleet of MCP servers in daily use. The
comments below are confined to the sections where that
operating experience gives us standing, principally Section 4.
The taxonomy gets the central fact right: in agentic systems,
harm is a property of a trajectory of actions, not of a single
response. Three gaps separate the draft from the systems it
will be used to assess: it does not name the authorization
point where actions are actually decided, it does not name
the action paths that bypass tool mediation entirely, and
several mitigations it lists are silently provider-dependent.
Each is correctable in the final edition, and each comment
below proposes specific text-level remedies.

## Comments

### 1. Section 4.1.1: The workflow stages omit the authorization point

The four stages (task instructions, planning, execution,
observation) describe the agent's loop accurately. They do
not describe the control loop that operated runtimes place
around that loop, and the omission matters because attacks
and mitigations both attach at the missing point.

In our runtime (phlow), every proposed action passes a
deterministic decision function before execution: a pure
function of the proposed action, the current state, and an
explicit policy, which returns allow, deny, or escalate to
the operator. Operator-approved checks are a named class in
the system, not a configuration detail. The same pattern
governs device actuation in our haptics MCP server, where a
single decide() gate mediates every command and denial is
the default for anything the policy does not affirmatively
permit.

This decision point is where several of the draft's own
attack classes land. Approval fatigue, policy tampering,
and escalation-channel spoofing are attacks on the
authorization point specifically; they fit none of the four
stages cleanly, because the agent's loop is intact while the
control around it fails. We recommend the final edition name
authorization as a fifth stage or, if the four-stage loop is
retained for fidelity to the literature, as a cross-cutting
control point drawn across the planning-to-execution
boundary in Figure 7, with its attack surface described in
Section 4.1.1.

### 2. Section 4.2: Action-level policy enforcement is the right mitigation; its principal is underspecified

The draft's treatment of action-level policy enforcement
(evaluating each proposed action, or the full trajectory,
against an explicit safety policy before execution) matches
deployed practice, and the draft is correct that trajectory
reasoning is required where individual steps appear benign.
One correction. The draft locates policy with "the developer
or deployer." Operated systems have a third principal: the
operator, a human (or a separate supervisory process) who
approves specific actions at runtime, under policies the
developer and deployer set in advance. The distinction is
not clerical. Developer policy, deployer policy, and
operator approval fail in different ways. They are attacked
in different ways, and they are audited in different ways. The
terminology section should define all three and assign each
mitigation in Sections 4.2 and 4.5 to the principal who
actually operates it.

### 3. Section 4.5: Name the unmediated action path

Section 4.5 is the strongest section in the draft. Tool
poisoning, rogue MCP servers, the rug pull variant, and the
tool/skill distinction (a tool's outputs enter the context
as data; a skill is loaded and followed as trusted guidance)
all match what a fleet operator observes. The rug pull
analysis in particular identifies the correct mechanism:
the attack is a versioning failure, in which a definition
approved once is silently replaced.

Two additions would make the section usable as an audit
reference.

First, the mitigations should name the control the rug pull
implies: immutable version identifiers for tool and skill
definitions, with any change to a definition treated as a
new approval event. Signing proves origin. It does not by
itself prevent post-approval substitution. A pinned,
hash-identified definition that the runtime re-verifies at
load time does.

Second, and more fundamental: a gate mediates only the
actions that pass through it. Real agents act through paths
that never become tool calls: code the agent writes and
executes directly, shell access, calls made by sub-agents
under delegated authority, scheduled jobs the agent creates
that fire after the session ends. An assessment conducted
in the draft's vocabulary can certify the mediated surface
completely while the unmediated paths carry the entire
risk. We recommend the taxonomy name this explicitly, as a
term (we suggest "unmediated action path") and as a coverage
question in Section 4.5's mitigations: for each action class
the system can perform, which path carries it, and does any
policy enforcement point sit on that path? Gate coverage,
not gate quality, is the property that fails first in
practice.

### 4. Section 4.1.2: Decomposition defeats per-action gates, and the draft should say so at the gate

The decomposition attack entry (NISTAML.067) correctly
observes that defenses may need to reason over sequences
rather than individual requests, and Section 4.2's
trajectory-level monitoring follows from it. The implication
for action-level enforcement deserves one explicit sentence
in Section 4.2: a per-action gate evaluates actions, not
intent, and a decomposition in which every step is
individually policy-compliant passes a correct gate. This
is a limit of the mitigation class, not an implementation
defect, and standards language that does not state the limit
will be read as claiming the property. Coverage in space
(every action path mediated) and coverage in time (the
trajectory evaluated as a whole) are separate properties.
The final edition should assess mitigations against both.

### 5. Section 4.4: Memory writes are actions and should be gated as actions

The memory poisoning entry (NISTAML.062) is accurate,
including the decoupling of injection time from exploitation
time. The mitigations discussion, however, treats memory
almost entirely from the retrieval side: what the agent
reads. From the operator's side, the prior question is what
the agent was permitted to write. In a mediated runtime, a
long-term memory write is an action with persistence, and it
can be subjected to the same decision function as any tool
call: provenance of the content, privilege of the source
that produced it, and operator approval for writes that
originate in untrusted data. We recommend adding
memory-write mediation to the mitigation set in Section 4.4.
It does not solve poisoning of external knowledge bases the
operator does not control. It closes the specific hole the
draft documents best, the dormant payload planted through a
single untrusted tool call.

### 6. Section 4.3: Signing proves the publisher; the operative control for local models is provenance plus probing

The draft's supply chain section is candid that signing and
transparency logs do not protect against a publisher who
poisons a model before signing it. For operators who run
local weights (our runtime serves local models through
rose), the consequence should be stated plainly: benchmark
evidence alone is not an adoption criterion for a
third-party fine-tune. Published work in 2026 (Microsoft's
"Trained to betray" result) showed that roughly one percent
poisoned fine-tuning rows could teach tool-misuse behaviour
that standard benchmarks scored as clean. Our adoption rule,
adopted in response, is provenance verification plus a
behavioural probe targeted at tool use, before any
third-party fine-tune serves an agent. We recommend Section
4.3's mitigations name this pairing (provenance check,
behavioural probe) as the control for the pre-signing
poisoning case, since it is the case the draft identifies
and then leaves without a mitigation.

### 7. Sections 4.2 and 4.5: Several mitigations are provider-dependent; mark them

Section 4.2 lists account-level monitoring by model
providers as a mitigation against agentic misuse campaigns.
For a self-hosted deployment there is no provider. The
account, the monitor, and the adversary's target are all
inside the operator's own perimeter, and the mitigation as
written does not transfer. The same applies, in lesser
degree, to mitigations that assume provider-side telemetry
or provider-enforced rate limits. None of this argues
against listing them. It argues for a marker. We recommend
the final edition tag each mitigation in Section 4 as
provider-dependent, deployer-operated, or runtime-resident,
so that an assessor working from the taxonomy can tell
which mitigations a local-model deployment must re-implement
rather than inherit.

### 8. Terminology: Three recommendations

(a) **"SI systems" will not survive contact with the field.**
The systems being hijacked, poisoned, and decomposed today
are ordinary deployed agents, and a terminology anchored to
"super intelligence" invites assessors to scope the document
away from the systems in front of them. The definitions
should be stated over "agentic systems" plainly, with the
SI framing, if retained at all, confined to the introduction.

(b) **Promote the tool/skill distinction to the glossary as
a load-bearing definition.** Section 4.5's observation:
tool outputs are data; skills are trusted guidance that may
persist across sessions: is the single most
security-relevant terminological distinction in the draft,
and it currently appears mid-section. It belongs in the
glossary with the same status as the attack terms, because
procurement and audit language will need to cite it.

(c) **Distinguish vector from outcome in the agentic index.**
Agent hijacking (NISTAML.061) is an outcome; indirect prompt
injection (NISTAML.015) is a vector that produces it, among
others. The index lists both as attack types without marking
the difference, which will double-count incidents in any
reporting regime built on the index. A one-column annotation
(vector / outcome / objective) in the Agentic SI Attacks
Taxonomy Index would prevent that.

### 9. Scope: One boundary case for the annex

We do not object to the exclusion of non-adversarial
failures from the taxonomy; a taxonomy of attacks should
describe attacks. But the boundary case is operationally
common and currently homeless: the agent that exceeds its
task with no adversarial input at all, through accumulated
context drift, a misread instruction, or a tool that returns
more authority than its description promised. The same
authorization point that stops a hijacked action stops this
one, which is why operators will reach for this document
when it happens. A short annex mapping the boundary (which
failure classes sit outside the taxonomy, and which of its
mitigations nonetheless apply to them) would cost two pages
and save every assessor from re-deriving it.
